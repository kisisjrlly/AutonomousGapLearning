## 决策 #001 - 渐进式改进策略

**日期**: 2026-09-17  
**决策者**: Claude (Project Manager) + User  
**类型**: 🟢 已确认

### 背景
代码库已有GRU记忆机制和episode内多次尝试支持，但缺少Context-Aware设计。

### 决策
采用**渐进式改进**而非重写：
1. 先验证GRU是否已经在利用历史
2. 基于验证结果决定是"增强"还是"重构"
3. 保留现有能力，逐步增加新功能

### 理由
- 降低风险：避免丢失已训练的基础能力
- 快速验证：2天内就能知道GRU状态
- 灵活调整：根据实验结果选择最优路径

### 影响
- 项目启动延迟2周（用于基线验证）
- 总体时间线可能缩短（避免重复工作）

## 决策 #002 - 仿真优先，真机并行准备

**日期**: 2026-09-17  
**决策者**: Claude (Project Manager)  
**类型**: 🟢 自主决策（基于HANDOFF.md的硬件问题记录）

### 背景
HANDOFF.md记录了GPU硬件问题，真机时间线不确定。

### 决策
- **主线**: 专注仿真验证，完成M1-M6
- **并行**: 准备真机安全协议和部署脚本
- **切换条件**: 硬件修复后，立即启动M7真机测试

### 理由
- 避免被硬件阻塞：仿真工作可以持续推进
- 降低风险：先在仿真中验证零碰撞能力
- 提高效率：硬件修复时，软件已就绪

### 影响
- M7真机验证的启动时间取决于硬件修复
- 如果硬件长期无法修复，项目将以"仿真验证完成"为终点

## 决策 #003 - 三阶段训练流程

**日期**: 2026-09-17  
**决策者**: User + Claude  
**类型**: 🟢 已确认

### 背景
用户明确区分了"训练阶段（允许撞墙学习）"和"部署阶段（零碰撞推理）"。

### 决策
实施三阶段训练：
1. **Phase 1**: 基础技能（允许碰撞）
2. **Phase 2**: 上下文学习（限制碰撞）
3. **Phase 3**: 零碰撞强化（强制安全）

### 理由
- 符合用户目标：训练时学基础，部署时纯推理
- 降低风险：渐进式加入安全约束
- 可验证性：每个阶段都有明确的成功标准

### 影响
- 训练时间延长：需要完整走完三个阶段
- 验收标准清晰：Phase 3必须达到零碰撞
